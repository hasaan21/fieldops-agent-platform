# Week 5: Applied ML and MLOps on Databricks

**Time:** about 25 hours.
**Outcome:** three models (urgency, job duration, asset failure) trained with honest evaluation, tracked and registered in MLflow with champion/challenger aliases, served to the agents as tools, and the same pipeline deployed to Databricks as an asset bundle. Plus a failure-mode analysis that turns eval failures into a ranked backlog.

## Why it matters

AI engineering roles increasingly expect applied ML alongside LLM work: classification, forecasting and predictive maintenance, MLOps on a platform such as Databricks or SageMaker, and failure-mode analysis with pandas, SQL and embeddings. Field service is full of classical ML problems that an LLM is the wrong tool for: how long a job takes, which boiler fails next month, how urgent a message is when the LLM provider is down. Interviewers want to see that you frame the problem before you pick the model, and that you can prove a model makes the *agent* better.

## Concepts

### Framing first
| Model | Framing | Metric that matters | Why that metric |
|---|---|---|---|
| Urgency (`ml/train_urgency.py`) | 4-class text classification | macro-F1, **emergency recall**, calibration (log loss, ECE) | Under-triaging an emergency is the costly error; the agent acts on the confidence |
| Duration (`ml/train_duration.py`) | Regression with intervals | MAE vs a baseline, **interval coverage** | Slots are sized from a range, not a point |
| Asset failure (`ml/train_failure.py`) | Discrete-time hazard: P(fail in next 30 days) per monthly snapshot | **PR-AUC, precision@5%, lift** | Rare positives; the team can only visit the top 5% |

### Leakage and splits (`ml/features.py`)
- Only use features known *at prediction time*: no duration or first-time-fix in intake features.
- **Time-based splits**: train on the past, test on the future. Random splits leak seasonality and trends.
- **Grouped splits**: snapshots of the same asset are correlated, so hold out 20% of assets entirely and report `pr_auc_unseen_assets` separately.
- **Label noise**: dispatcher urgency labels disagree with `true_urgency` about 11% of the time. Accuracy against noisy labels is capped near 0.89; score against the clean label too so you don't chase noise.

### Models and the reasoning behind them
- **TF-IDF (word + char n-grams) + linear model** is the baseline that's hard to beat on short text: about 1ms per call and robust to typos. `transformer_urgency.py` fine-tunes DistilBERT with a plain PyTorch loop to compare.
- **Gradient boosting** (`HistGradientBoosting*`): native categoricals (`categorical_features="from_dtype"`), missing values, **monotonic constraints** (risk can't go *down* as servicing gets more overdue), and quantile loss for intervals. The plan said LightGBM; on macOS it needs `brew install libomp`. sklearn's implementation uses the same algorithm with no system dependency. The lab compares the two.
- **Conformalized quantile regression** (`cqr_offset`): raw quantile GBMs under-cover. Calibrate the interval on a held-out recent slice so a nominal 80% interval really covers 80%.
- **Calibration**: if code acts on `predict_proba` (thresholds, upgrades, ranking budgets), the probabilities must mean what they say. `CalibratedClassifierCV(method="isotonic")`, reliability tables, ECE.

### MLflow, the registry and aliases (`ml/common.py`, `ml/serving.py`)
- Every run logs params, metrics, artifacts (confusion matrix, calibration table, feature importance) and the model with an input example (which gives a signature).
- **Aliases, not stages**: a new version gets `@challenger` and becomes `@champion` only if it beats the current champion. Serving loads `models:/name@champion`, so promotion is a metadata change with no redeploy. The same API works on Unity Catalog.
- **skops, not pickle**: MLflow 3 serialises sklearn models with skops, which refuses unknown types at load time (unpickling is code execution). We list exactly the types our pipelines use in `SKOPS_TRUSTED`. Never "trust everything".
- **Serving input = raw business fields.** Casting (strings to categoricals, DataFrame to text) lives *inside* the pipeline (`to_category`, `to_text`), so the API contract is plain JSON and training/serving can't drift.
- **Model cards** (`docs/model_cards/*.md`) are generated by the training run, so they never go stale.

### Models as agent tools (`tools/ml_tools.py`, `agents/job_intake/graph.py`)
- `estimate_job_duration` and `asset_failure_risk` are registry tools. The LLM sends IDs; the server resolves the asset through the **tenant-scoped CRM** (a t1 request for a t2 asset raises `TenantIsolationError`) and builds features next to the model.
- In the intake graph, the booking proposal carries `estimated_hours` and `asset_risk` for the reviewer, and a high-risk asset raises a `maintenance_suggested` flag.
- **Asymmetric second opinion**: the urgency model may only *upgrade* to emergency, at high confidence. Other disagreements are flagged, not acted on.
- **Graceful degradation**: no registry means transparent fallbacks (`source: "fallback"`), so the agent never fails because a model is missing, and traces show which path served.

### Databricks (`databricks/`)
- **Asset bundle** (`databricks.yml`): schema, a 5-task job (ingest, features, train, serve, failure modes), a weekly schedule, dev/prod targets. `sync.paths` ships `capstone/` so notebooks import the same feature and training code as local runs.
- **Delta + Unity Catalog** (`01_ingest_delta.py`): managed tables with comments; row filters on `tenant_id` mirror the Postgres RLS policy.
- **Feature Engineering in UC** (`02_feature_table.py`): a time-series feature table keyed on `(asset_id, snapshot_date)`. **Point-in-time lookups** (`timestamp_lookup_key`) make leakage structurally impossible. `fe.log_model` packages the lookup so serving needs only keys.
- **Registry and promotion** (`03_train_register.py`): `mlflow.set_registry_uri("databricks-uc")`, register `catalog.schema.asset_failure`, aliases as above.
- **Model Serving** (`04_serving.py`): resolve `@champion`, update the endpoint only if it changed, scale-to-zero for dev, inference tables for monitoring, and traffic splits for canaries.

## Results on the synthetic data

Reproduce: `uv run python -m capstone.ml.train_urgency` (and `train_duration`, `train_failure`), then `uv run python -m capstone.evals.ml_ablation`.

**Urgency** (450 test jobs, time split; label-agreement ceiling 0.893):

| model | macro-F1 | emergency recall | acc. vs true label | log loss | ECE |
|---|---|---|---|---|---|
| TF-IDF + calibrated logistic regression (**champion**) | 0.893 | 0.932 | 0.998 | **0.41** | **0.015** |
| TF-IDF + Complement NB | 0.895 | 0.932 | 1.000 | 1.80 | 0.107 |

**Duration** (MAE in hours): category-median baseline 0.751; gradient boosting **0.620** (17% better). Raw p10–p90 coverage was **0.67**; after conformal calibration (offset 0.26h) it is **0.80**, the nominal level.

**Asset failure** (base rate 9.1%):

| model | PR-AUC | ROC-AUC | precision@5% | lift@5% | PR-AUC unseen assets |
|---|---|---|---|---|---|
| logistic regression (**champion**) | 0.327 | 0.714 | 0.468 | 5.1x | 0.518 |
| HistGB with monotone constraints | 0.266 | 0.685 | 0.372 | 4.1x | 0.418 |

The linear model wins because the synthetic hazard *is* logistic in its features: the model matches the data-generating process. On real telemetry with interactions, expect boosting to win. Either way, the selection code picks the winner on the metric; nobody's favourite model gets in by default.

**Did the agent get smarter?** (`docs/eval-reports/ml-ablation.md`)
- Triage metrics are flat with ML tools on (urgency 0.951 both ways, outcome 1.000), as designed.
- All 118 booking proposals now carry a duration range; 47 carry an asset risk score; 3 raise a maintenance suggestion.
- Slot sizing on historical jobs: the conformal p90 policy has the same 12.4% overrun rate as booking each category's p90, using **3.92 vs 4.13 booked hours per job** (about 5% capacity back). A fixed 2-hour slot overruns 82% of the time.

### War story: the model that made the agent worse
The first ablation used Complement Naive Bayes as the urgency champion. It was picked on macro-F1 alone (0.895 vs 0.893, inside one CV standard deviation). With ML on, `urgency_score` *dropped* by 0.031. Six wrong upgrades to "emergency" came from messages like "Something's broken in the plant room", which are vague, out of distribution for a model trained on job descriptions, and scored 71% confident. Naive Bayes probabilities are notoriously overconfident (ECE 0.107). The fix was in **model selection**, not the threshold: among models within noise on F1, prefer the lowest log loss, because the agent acts on the confidence. After the fix: zero wrong upgrades, metrics flat. This is the best ML story in the repo for interviews: an offline metric that looked fine, an agent-level eval that caught it, and a root cause tied to how the model is *used*.

### Also caught this week: stale eval fixtures
Adding label noise to the generator changed the random sequence, so customers' phone numbers changed. The frozen dev/test JSONL still pointed at the old phones, and `outcome_correct` "regressed" from 0.97 to 0.73 overnight. The agent was fine; the fixtures weren't. `datasets.py` now stores a fingerprint of the world in `_meta.json` and raises `StaleDatasetError` on mismatch. Lesson: version eval datasets *with* the data they reference.

## Failure-mode analysis (`analysis/failure_modes.py`)

`uv run python -m capstone.analysis.failure_modes` produces `docs/eval-reports/failure-modes.md`:
1. **SQL slices** (sqlite in-process; Spark SQL on Databricks) by metric, failure mode, channel and tenant, with each slice's share of runs.
2. **Embedding clusters**: KMeans over failing messages with k chosen by silhouette, labelled by each cluster's most *distinctive* TF-IDF terms (lift over the corpus mean, not raw frequency).
3. **Impact = frequency × severity.** `SEVERITY` makes business cost explicit (a missed safety escalation = 20, an over-long reply = 0.5). The output is a ranked backlog with a suggested fix per cluster.

On the first offline run it found that out-of-scope requests failed 41% of the time (the highest-cost slice), and that vague "it's stopped working" messages form their own cluster. Week 6 follows the out-of-scope slice to its root cause, which turned out to be half data bug, half classifier gap.

2. **LightGBM comparison (required):** `brew install libomp`, add an `LGBMRegressor` candidate to duration with the same features (`categorical_feature`, `objective="quantile"`), and compare MAE, coverage and training time. Write down which you'd ship and why.

Then build a **paraphrased** test set (50 messages, typos and slang, written by you or an LLM and checked by you) and compare TF-IDF vs the transformer there. That's where the transformer should earn its 100x cost, or not.
4. **Survival framing (stretch):** fit a discrete-time hazard with `lifelines` or `scikit-survival` on time-to-failure with censoring; compare C-index and the 30-day ranking with the classifier.
5. **Databricks (required):** sign up for [Free Edition](https://www.databricks.com/learn/free-edition), `databricks auth login`, then `cd databricks && databricks bundle deploy -t dev && databricks bundle run -t dev fieldops_ml_pipeline`. Screenshot the UC lineage graph (table → feature table → model → endpoint).

## Production bar
- Time/grouped splits, a baseline in every model card, and metrics chosen for the decision the model drives.
- Calibrated probabilities wherever code thresholds them; interval coverage reported, not assumed.
- Registry aliases for promotion; serving pinned to `@champion`; a rollback is moving an alias back.
- Safe serialisation (skops with an explicit trusted-type list); signatures and input examples logged.
- Agent-level ablation before an ML tool is turned on; fallbacks labelled in traces.
- Retraining is scheduled, and promotion is automatic only when the challenger wins on the same window.

## Interview questions
1. *"How would you predict job duration?"* Framing (point + interval), leakage (only intake-time features), a time split, a category-median baseline, GBM with quantile loss, conformal calibration for coverage, MAE and coverage as metrics, and the business metric: overruns vs booked hours. Monitor drift by tenant and trade.
2. *"Your classifier has 0.90 F1 offline but made the agent worse. Why?"* Distribution shift (descriptions vs customer messages), overconfident probabilities used as a gate, threshold set without calibration, eval set not covering vague inputs. Fix with calibration-aware selection, asymmetric policies and an agent-level ablation in CI.
3. *"PR-AUC or ROC-AUC for predictive maintenance?"* PR-AUC (and precision@capacity) under heavy imbalance; ROC-AUC looks good while precision in the top-k is poor. Always report the base rate and lift.
4. *"How do you deploy a new model version safely?"* Register as challenger, evaluate on the same window as the champion, shadow or canary traffic via a serving traffic split, watch inference tables and online metrics, promote by alias, roll back by alias.
5. *"Why a feature store?"* Point-in-time correct training sets, one definition for training and serving, online lookup by key, lineage in UC, and reuse across models. Without one, people reimplement features in the serving path and they drift.
6. *"When would you use a transformer instead of TF-IDF?"* When text is varied (paraphrase, slang, multilingual), there's enough labelled data or a good pretrained base, and the latency/cost budget allows it, *proven* on a realistic test set. Otherwise TF-IDF plus a linear model is a strong, cheap, explainable baseline and a fallback when the LLM is down.
